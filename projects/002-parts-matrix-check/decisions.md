## 提案 (構想書とコードに入れたが、まだ了承をもらっていないこと)

| No | 提案 | 理由 |
|---|---|---|
| P-01 | 言語は Excel VBA。追加のソフトは使わない | 依頼でも VBA の見込みだった。結合セルの情報を読めるのは VBA。Power Query や関数だけでは結合が読めない |
| P-02 | 両方を「品番 × 仕様」の縦長の一覧に直してから比べる | 形の違いを読み取りの所だけに閉じ込められる |
| P-03 | マトリックスの形は、人がマウスで 3 か所を教え、ツールが覚える | 形がばらばらなので、自動で当てると読み違える。確認用のツールが読み違えるのは危ない |
| P-04 | 形の自動提案は第二段階にする | まず確実に動く方式を作る。自動提案は、その上に足せる |
| P-05 | 仕様の呼び名の違いは「仕様対応表」で合わせる。未設定が残っていたら照合を始めない | 黙って飛ばすと、比べていないのに「合っている」と見えてしまう |
| P-06 | 元のファイルは読み取り専用で開き、書き換えない。結果は別のブックに出す | 大事な元データを壊さない |
| P-07 | マクロはツール用のブック 1 つに入れる。マトリックスの側にはマクロを入れない | 設計者ごとのファイルを変えずに済む |
| P-08 | 読み取った結果を必ずシートに見せる | 正しく読めたかを人が確かめられる。Copilot で 1 段階ずつ作りやすい |
| P-09 | 結果は、照合のたびに新しいブック 1 つにまとめて保存する (ツール用ブックの中のシートには出さない) | 赤ペンを入れた紙の代わりに、記録として保管できる |
| P-10 | チェックできている証拠として、消し込み・検算・抜き打ち・自己診断・抜き取り確認の 5 つを持つ | 食い違いだけを出すと、「見ていない所」があっても分からない |
| P-11 | 検算が 1 つでも合わなければ、判定を「検算が合わない (この結果は使わないこと)」にする | 読みもらしがあるのに「一致」と出るのが、一番危ない |
| P-12 | コードは、マクロ付きブックではなく、マクロなしのブック + コードのファイルで渡す | マクロ付きのファイルは、社外からの持ち込みで止められやすい。ここでは Excel で確かめられないため、動く保証の無い `.xlsm` を渡さない |
| P-13 | 作る側の確かめは、LibreOffice の VBA 互換の機能で行う | この環境に Excel が無い。コードを 1 行も動かさずに渡すよりは確かである |

## 依頼の文の読み取り (自分の解釈)

- 「出力ファイルは Excel のファイルにまとめる」は、次の 2 つの意味のどちらにも取れたので、両方を満たすようにした。
  - ツールが出す結果を、Excel のブック 1 つにまとめる (構想書の 8 章)。
  - ここから渡す成果物を、Excel のブックにまとめる (`handover/照合ツール_ひな形.xlsx`)。
- 依頼の文に「各社の仕様」とあったが、前後の文から「各車の仕様」の意味として扱った (構想書の Q-06 で確認する)。
